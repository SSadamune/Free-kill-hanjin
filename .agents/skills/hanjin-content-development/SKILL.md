# 汉晋内容开发

让规则语义、卡面描述、新月杀实现及测试相互对应；不把现有代码或测试通过当作规则裁定。本 skill 的流程适用于不同开发者和 agent，不要求 Codex、DSH 或多 agent。

## 从短指令确定任务

用户只需给出动作和范围，例如：

| 指令 | 默认执行方式 |
| --- | --- |
| 按照 `hanjin-content-development` 审阅蜀势力标准包 | 进行规则与实现路径审阅，暂不改技能实现或测试逻辑 |
| 根据已确认规则实装蜀势力标准包 | 在当前工作区实装、审阅并验证，持续推进到约定范围完成；不只给计划 |
| 根据已确认规则安排 DSH 实装蜀势力标准包 | 由当前负责人拆批、判断规则与测试重点并审阅，DSH 实现限定批次；按下文交接约定推进 |

用户明确要求审阅现有代码、修复故障、编写规范描述或限制修改范围时，按该具体任务执行，不强行切换成整包规则研究。未指定委派时，默认当前 agent 完成；用户已明确配置协作方式时遵循该配置。单 agent 可分阶段自查，不假称有独立审阅者。

明确指定 DSH 等执行工具时，先确认工具可用；不可用须说明缺少的能力，不假称已派发，也不静默换成另一提供方。此时可继续不依赖该工具的资料核对，依赖部分等用户选择。

## 自行补齐上下文

1. 读取适用的 `AGENTS.md` 和[开发指南](../../../docs/development/README.md)，检查当前分支、工作区及已有修改；保留其他任务内容，不擅自切分支或覆盖。
2. 按[标准武将表](../../../rules/standard-generals.md)、[开发状态](../../../docs/development/status.md)及[实现导航](../../../docs/development/implementation/README.md)确定编号、技能、已实现部分、关联翼从和现有验证。使用已确认的项目范围；默认不把君主版、其他版本或未指定包混入。
3. 用户未粘贴原文时，自己读取仓库资料和对应逐将规范；不要求用户重复提供已经存在的来源、路径、测试命令或工作流。前一会话未落盘的裁定不视为已知。
4. 只有范围／版本确实无法确定、关键资料缺失、已有依据相互冲突或确需新增裁定时提问，给出具体场景、依据和分歧。可独立推进的其他部分继续处理；常规实现选择自行决定。

## 规则审阅

- 区分[外部参考资料](../../../docs/README.md#外部参考资料)、[项目设计与裁定](../../../rules/README.md)和[规则集工作底稿](../../../rulebook/README.md)。具体基础条文引用 `rulebook/`，结合已确认汉晋差异；只查与本次内容相关的原文，不加载全部参考库。
- 按时机、条件、目标、消耗、效果及来源理解技能，考虑主副将、明暗置、势力和敌友关系。已有术语或已确认裁定能够解决的问题自行核对，不重新要求用户确认。
- 新月杀源码用于核对锁定引擎的接口、事件和执行流程，不反过来决定技能含义。源码与规范不一致时标明程序差异；建议与未决事项保持其状态。用户确认后，由负责人将裁定及依据写回对应逐将规范或公共规范，避免后续实装依赖聊天记忆。
- 简短交付范围与来源核对、关键结算／实现方向、真正未决问题和少量核心验收重点。按需更新现有规范与实现记录，无需为交接另造整包说明或逐规则测试清单；卡面文本、规则抽象和代码各有职责，实装报告不能直接充当正式条文。未执行的测试只记为计划。编写规范描述时读取[描述指南](../../../docs/development/normalized-descriptions.md)。

## 实装与审阅

- “根据已确认规则实装”允许开始实现，但不使既有待裁定事项自动获批。先核对相关规范；确有阻塞的分支保留待定并报告，其他已明确部分继续推进。
- 按实际复杂度分批。同类常规技能可合批；新客户端入口、公共机制或复杂濒死／用牌流程先交能触达主要效果的小批次。每批尽早核对客户端／服务端、选择／执行、可选／必然、消耗／后续效果、当前技能／已建立持续效果这些关键边界。
- 依 `dependencies.lock.json` 核实回调、事件数据类型与方法所属对象。客户端判定不依赖服务端私有字段；优先复用公共目标、转换、应变与武将来源机制，避免重复结算。玩家交互必须通过正式扩展发布，不用开发本体补丁代替交付。
- 按[测试规范](../../../docs/development/testing.md)复用公共夹具、请求辅助和模板，验证真实主流程及本批风险；先定向、稳定后默认全量，需要发布或改变加载路径时构建并检查安装包。共享运行时只由一个指定执行者同步和测试，单 agent 即自身执行。
- 审阅后只修实质问题；每项意见交代已改且验证、已改待验证或未改及原因。失败给出最短证据链，两次无进展即交回定位结果与最小选项，不靠猜接口、删断言或重跑刷绿。仅遇同类问题时查[故障案例](../../../docs/development/lessons.md)。

## 指定委派时的交接

当前负责人承担拆分、规则判断、测试取舍、审阅与最终交付；委派执行者承担限定实现和验证。角色可以由不同工具承担，不因此改写项目流程。单 agent 无须制造委派环节。

- 每轮传递一个目标、允许文件、少量核心验收、测试执行者、约 10–15 分钟阶段预算和所需资料链接；接收方须读取本 skill 与相关规范，不假设它已加载聊天。不要一次压入整包边界、完整测试映射或独立子代理审阅。
- 委派执行者约每 5 分钟简报，到预算或里程碑交回实际阶段成果；预算不是已设置的硬超时。两次无进展、规则冲突或需扩大范围时及时交回，不静默扩大工作。
- 负责人核对证据并逐项闭合审阅意见，再给下一轮范围；规则类文档由负责规则判断的角色维护，委派执行者默认只读。等待与进度按实际工具支持的协议执行，不用外部轮询或自动化提醒追踪单次运行。

## 完成与交付

每批稳定后按[分类与检索约定](../../../docs/development/implementation/README.md)更新相应技能机制记录，并更新开发状态。区分规则确认、代码完成、自动化通过及客户端／联网／重连人工验收；沿用的历史结果标明原验证范围。

交付说明实际改动、真实执行命令与结果、未完成项或阻塞。用户无需重复指定上述步骤；只有新增限制、仓库外资料、未落盘裁定等才需要额外提供。默认不提交、推送或创建／更新 PR；已有明确授权时按其范围执行，不重复索要确认，创建或更新 PR 前读仓库模板。
