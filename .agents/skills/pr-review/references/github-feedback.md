# Publish or update GitHub feedback

- Write for the author reading GitHub. Apply the requested attribution, language and format. Explain the current conclusion and evidence without relying on private chat. Cite an earlier review only when useful and identify it by link and author or date. Link supporting code to the reviewed SHA and line. Include only verified, relevant follow-up paths. For a requested change summary, use the specified commit range and group by behavior. For a code suggestion, show the smallest relevant change and label an illustrative diff as such.
- Confirm repository, PR number and current head before publishing. Recheck affected findings and line anchors if the head changed. Use a timeline comment for general feedback, a review with `COMMENT` for bundled line comments when requested, and the exact existing object when asked to edit or reply. `APPROVE`, `REQUEST_CHANGES` and resolving a thread have distinct effects. Anchor inline comments with the current diff path, side and line, and pin the reviewed commit. Reply to an inline thread using its top-level comment ID. [GitHub review actions](https://docs.github.com/en/pull-requests/concepts/giving-reviews) · [Review comment API](https://docs.github.com/en/rest/pulls/comments)
- Use a connector that supports the authorized write. If an earlier permission denial applies to this connector and repository and access has not changed, use the authenticated CLI when permitted. Store multiline Markdown as UTF-8 and pass it through `gh pr comment <number> --repo <owner/repo> --body-file <file>`. Use structured JSON with `gh api --input` for an inline review when needed. When editing, verify the original author, object type and exact ID before writing. [CLI comments](https://cli.github.com/manual/gh_pr_comment) · [CLI API](https://cli.github.com/manual/gh_api) · [Timeline API](https://docs.github.com/en/rest/issues/comments) · [Review API](https://docs.github.com/en/rest/pulls/reviews)
- Distinguish a sandbox network failure from an invalid credential or a GitHub permission error. Follow the environment's approval mechanism for any authorized network call that needs it. Browser fallback makes sense when an appropriate signed-in session is available and the result can be verified. Transfer an actionable blocker or a finished draft when retrying would repeat the same failed approach.
- Check the target for an existing copy before writing. On timeout or unknown result, read the target timeline, review or thread before retrying. Verify the published record and return its link. If the user takes over or publication is blocked, give the complete copyable Markdown and distinguish a pending draft from published feedback.
