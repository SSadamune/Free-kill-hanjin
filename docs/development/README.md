## 一次内容开发

本流程不绑定模型或协作工具。负责人接收任务，承担规则判断、拆批、测试取舍、审阅与最终交付；执行者承担限定实现和验证。两种职责可以由同一开发者或 agent 承担，此时分阶段自查，不宣称经过独立审阅。默认由当前 agent 执行；用户明确指定或已配置委派时才使用对应工具。

1. 查对应规则条款、卡面描述及有关基础术语，确认时机、消耗、效果和来源，标明尚待裁定的部分；同时核对目标条件依赖的性别、势力、主副将位置等基础资料及加载结果，避免沿用引擎默认值。需要补规范描述时按[描述体系](normalized-descriptions.md)组织，不猜测或擅自扩充规则。
2. 按复杂度拆批，交代一个可交付目标、允许文件、少量核心验收和测试执行者。委派的阶段预算及交付方式见[内容开发 skill](../../.agents/skills/hanjin-content-development/SKILL.md)。同类常规技能可以合批；涉及新客户端入口、公共机制或复杂濒死／用牌流程时，先交能触达主要效果的小批次。并行批次数须与审阅和串行验证能力匹配，首个代表性流程尚未运行时，先缩小在制批次，避免积累大量未运行实现与测试。
3. 编码前按[回调执行端与房间访问](#回调执行端与房间访问)判定本批回调及辅助函数的执行端，采用对应模板；无需另写过程记录。按下方[复用现有实现](#复用现有实现)查找锁定版本的对应技能和项目公共代码。对本批有风险的入口，先核对客户端／服务端、选择／执行、可选／必然、消耗／后续效果、当前技能／已建立持续效果这些边界，由负责人尽早审阅少量关键接口或可运行流程，再扩展实现。常规接口沿用既有机制，不要求每个技能单独审批；接口行为不能代替规则裁定。
4. 执行者打通最小正常流程，尽早触达真实选牌、选人、提示、取消和确认；由指定执行者按[测试规范](testing.md)串行验证共享运行时。同类请求先运行一个代表性用例，确认回复格式、消费顺序和观察探针正确后再扩展。优先复用公共夹具、请求辅助与套件模板，不为每批复制一套略有差异的初始化代码。玩家功能按正式扩展加载路径实现。
5. 负责人审阅阶段成果，后续只修实质缺口。再次交回时，逐项说明审阅意见为“已改且验证”“已改待验证”或“未改／原因”，附对应位置和必要证据；负责人核对状态后再给下一轮范围。失败按最短证据链定位，两次无进展即交回，不连续猜接口或重跑刷绿。
6. 每批稳定后按[分类与检索约定](implementation/README.md)更新实际受影响的技能记录，引用真实命令结果并保留边界；规则变化由负责人写回对应规范。相关实现稳定后做一次默认全量，需要发布或修改加载路径时构建并检查安装包，再更新[开发状态](status.md)。提交及 PR 按 [AGENTS.md](../../AGENTS.md) 和[项目模板](../../.github/pull_request_template.md)执行，须有用户授权。

公共机制首次接入正式武将／卡牌，或改动影响其技能标签、位置限制、来源时，执行者须尽早验证一条正式内容经过实际公共入口的正常流程，再扩展同类内容。测试替身验证公共算法、直接调用技能效果验证局部效果，都不能代替这条连接流程；例如君主技能单独可用，不等于普通武将实际升变后会获得它。已有同类集成覆盖且相关约束未变时可复用，不逐将重复建立同样测试。

阶段交回沿用现有实现记录，说明实际经过的入口、观察到的关键结果，以及哪些只做了局部验证。负责人据此核对本批风险是否被真正触达，不把两个分别通过的局部套件合并解释为接线已通过。具体断言范围见[来源与连接流程验收](testing.md#来源与连接流程验收)。

需要委派时，交接只保留本批已确认差异、公共接口方向、文件边界及核心验收，详细依据链接到维护中的文档；不一次交付整包边界清单。不要假设接收方已读取当前聊天或自动加载项目 skill。规则类文件由负责规则判断的角色维护，委派执行者修改需按项目约定明确授权。

两次无进展交回后，负责人先检查具体失败证据，再选择修正接口、缩小复现或接手；没有新定位时，不把同一问题重新包装成下一轮任务。阶段预算不因催办或原样续派而重新计算，等待仍遵守工具的原生协议。

达到阶段预算仍未交回时，负责人要求执行者在当前动作收尾后交回已有文件、实际结果与阻塞，停止新增修复和测试；执行者无法响应时，按工具能力中止该会话，再核对遗留任务与测试槽后接手。工具的单次等待上限不作为继续开发的预算，不靠反复等待最终整包成果替代阶段审阅。

使用 DSH 时，注意当前 `dsh_send(checks=...)` 会自动附加子代理审阅要求。常规批次不传该参数，测试命令写在任务正文中，由负责人核对实际输出；如需工具原生复核，可在稳定交回后单独安排。工具附加文字不能代替项目对范围与审阅方式的约定。

## 回调执行端与房间访问

这是编码时的接口约束。客户端负责界面查询，服务端负责权威结算；本地单机也使用两端角色对象。`ClientPlayer` 没有 `ServerPlayer.room`。开始新增或修改技能前，先按锁定引擎确定回调执行端，再选下面的写法；不能从示例中复制服务端写法到界面回调。

| 回调职责 | 房间来源与写法 |
| --- | --- |
| 主动／转换技能的 `can_use`、`enabled_at_*`、`card_filter`、`target_filter`、`mod_target_filter`、`feasible`、`view_as`、函数式 `prompt`／数量限制／`expand_pile`、`interaction`，以及距离／禁止／目标修正等可能在客户端执行的查询 | 按两端共用查询编写；需要房间时统一使用 `Fk:currentRoom()`，只读公开状态；不得以 `player.room` 取得房间、将它作为房间参数传给别的函数，或用 `player.room or ...` 保留分叉 |
| `on_use(self, room, effect)` 等显式传入房间的服务端结算 | 使用传入的 `room` 校验并执行效果，不从角色重新获取房间 |
| 仅由服务端事件执行的 `can_trigger`、`on_cost`、`on_refresh` 等 | 核对事件执行端后可用 `player.room`；不能据此允许同文件中的界面查询也使用该字段 |
| 被多类回调调用的辅助函数／上游接口 | 限制由所有调用方决定；只要客户端可达，就按共用查询编写。显式接收 `room` 的辅助函数须由客户端调用方传 `Fk:currentRoom()`，不能仅修函数体而漏掉调用参数 |

既有实例／转换管理模块可以在明确的服务端分支内访问私有状态，在客户端分支只读公开摘要。区分两端的能力判定不等于使用该字段取得客户端房间；此类分流集中维护并验证两个分支，普通技能不得各自复制一套。

普通技能的选人、角色数、手牌数或体力值比较统一使用 `room:getPresentPlayers()`，两端都能读取，随移出和移回实时更新。汉晋服务端的 `getAlivePlayers()`、默认的 `getOtherPlayers()` 和公共选人请求也应用同一过滤。胜负、天然野心家与鏖战等明确计入移出者的规则读取原始名单。延时效果或固定目标直接取得角色对象时，在实际结算前用 `removed_targets.isPresent(player)` 复核。

公共查询示例（可供可用性、目标筛选和服务端复核共用）：

```lua
local function candidates(player)
  local room = Fk:currentRoom()
  return table.filter(room:getPresentPlayers(), function(other)
    return other ~= player
  end)
end

-- on_use 等结算入口始终使用引擎传入的 room。
-- 查询不改变状态；真正提交后仍在服务端复核规则与候选。
```

`Fk:currentRoom()` 在客户端应返回客户端房间，不授权读取服务端的 `logic`、私有 tag、暗将信息、未公开牌堆或剩余将池。客户端确需候选时使用既有公开同步接口；不能给 `ClientPlayer` 补一个服务端 `room` 代理。缺失房间或公开数据须核对调用上下文与同步接线，不能通过返回空候选／恒为 false 让技能悄悄失效。

计算在场角色时，客户端和服务端共用 `getPresentPlayers()`。`Room:getAlivePlayers()` 只在服务端可用。卡牌回归用真实出牌请求初始化手牌，再验证合法目标能从界面选中并确认。

编码与审阅都沿调用链检查：回调 → 本地 helper → 公共／上游函数及其参数。修改被双方使用的规则查询时，双方复用同一规则函数，避免界面和服务端分别手写“小势力”等算法。只有查阅引擎后确认的纯服务端回调才使用服务端字段；未知回调先定位调用处，不靠名称猜测。

默认客户端回归用于兜底，按钮查询、点击后进入技能、牌／目标筛选是不同路径。界面相关改动须触达本次改动对应的路径；检查范围和具体入口见[测试规范](testing.md#夹具与失败诊断)。无需为每个常规技能新增重复套件或过程文档。

## 普通主动技的次数声明

汉晋普通出牌入口在客户端更新按钮和确认状态时、服务端计次和结算前统一检查主动技声明的次数。效果上的 `max_*_use_time` 使用该效果的历史，骨架声明使用整个技能的历史，动态上限在当前玩家状态下计算。固定或动态上限写在与规则对应的声明层级即可。额外发动、辅助选牌和翼从逐实例次数沿用自己的入口与规则。

自定义 `can_use` 用于技能本身的条件。新月杀 v0.5.25 的默认阶段次数查询会被该回调覆盖，所以汉晋的普通出牌入口统一保留独立的次数检查。回归须通过实际 `PlayCard` 请求和服务端普通回包，直接调用 `on_use` 不经过这层检查。

## 公共武将操作的职责

业务技能通过已适配的公共操作入口执行升变、交换、移除或变更；公共操作负责按实际武将牌身份同步该操作涉及的技能来源及状态，不能仅因调用了引擎 `changeHero` 或发送了明置事件就认定同步完成。涉及暗将时须核对实际牌身份，不能以公开的 `anjiang` 代替旧牌；规则中的国战君主技等概念须核对引擎标签的获取条件，不能按名称直接套用身份模式限制。

来源同步的完成条件为：旧牌不再提供的来源已撤回，新牌合法来源已安装，仍存在的其他来源保持有效。具体技能不各自复制底层清理逻辑；已出现的相同清理交给公共接口复用。交换的牌堆／次数迁移、升变的体力收益等由各操作入口负责，不把不同业务全部塞进技能来源清理接口。接口及现有分工见[公共武将来源职责](implementation/general-exchange.md#公共武将来源职责)，后天附将技能沿用该页的来源接口。

## 复用现有实现

- 编码前先查项目已有技能、公共模块和锁定上游的同名／同效果实现。常用位置为 `pkg/`、`.dev/runtime/FreeKill-release/packages/standard/pkg/skills/` 及依赖包；先按技能名查，再按关键事件或接口查。短时找不到就说明未找到的范围，继续已有依据支持的工作，不把搜索扩成整库研究。
- 有可用实现时，从中保留符合规则的流程，只改汉晋差异及正式牌名、技能来源等接线；同名不等于同规则。已有项目公共机制优先直接调用，未实装的空壳不算可复用效果。当前安装的接口与依赖版本仍须核对。
- 项目内同名且效果相同的技能只注册一份，不同武将引用同一个技能 ID，不按武将各建一份技能。来源与明暗置由引擎及项目公共机制处理，不能仅因所属武将不同就拆 ID。只有明确的版本差异或已核实的兼容限制才保留独立 ID，并说明原因；其中相同效果仍共用实现。同效果但不同名的技能可共享效果代码，不机械合并技能身份。已有重复在涉及这些技能的开发中合并，并核对来源归属及旧 ID 引用；不要求本轮迁移全部旧代码，也不为潜在相似技能预建通用框架。
- 在已有实现记录的“实现与接口”中简记实际读过的参考路径、关键差异及采用的共享入口；同一批可合并记录，委派时传递已定位的路径。不另建逐技能调查表，也不把“要求查阅”或结构相似当作实际读过的证据。审阅重点看差异、复用接线和主要效果，不重验上游全部基础行为。

## 新会话入口

使用 [hanjin-content-development](../../.agents/skills/hanjin-content-development/SKILL.md) 时，通常只需给出动作和范围：

> 按照 `hanjin-content-development` 审阅蜀势力标准包。

> 根据已确认规则实装蜀势力标准包。

需要指定执行工具时：

> 根据已确认规则安排 DSH 实装蜀势力标准包。

skill 已规定上下文查找、规则核对、拆批、验证、审阅与收尾。agent 应自行核对当前分支、工作区、原文、逐将规范及状态，不要求用户重复提供仓库已有内容。整包可一次审阅，实装按复杂度分批；“实装”要求推进到范围完成，不只输出计划。未决规则不因该指令自动获批。

仅需额外提供仓库中没有的资料或裁定、特殊版本／范围限制，以及提交、推送或 PR 的授权。已有明确授权无需重复确认。新会话不能假设读过旧聊天，应以落盘记录为依据。不支持 skill 加载的 agent 可直接读取上述文件；实际自动加载能力取决于所用工具。

规则集、外部汉晋资料和用户裁定用于确定游戏语义；新月杀源码用于核对当前接口与执行流程，不能反过来替代规则。复用现有逐将规范与机制记录，不要求每次先编写整包实现说明或完整自动化测试清单。

## 维护约定

`docs/rules/` 保留项目规范的角色及稳定引用，不能将其直接视为《汉晋规则集》。正式条文在 `rulebook/` 独立编纂，按外部基准的结构与精炼文风表达，并链接依据。编纂内容需要拆分时更新引用，旧引用确有兼容价值时保留入口，不复制两份正文。规范、API 文档和状态的变更各有依据；不要把状态过期误当规则变更。

本次整理把原规则文件的工程章节移到 `implementation/`，保留接线和验收细节，未逐一将历史卡面文本重写成规范描述。少量既有条款仍含与程序有关的解释，后续编纂时按语义核对逐步整理，不以机械删词改变已确认规则。
