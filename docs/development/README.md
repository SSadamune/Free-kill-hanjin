## 一次内容开发

本流程不绑定模型或协作工具。负责人接收任务，承担规则判断、拆批、测试取舍、审阅与最终交付；执行者承担限定实现和验证。两种职责可以由同一开发者或 agent 承担，此时分阶段自查，不宣称经过独立审阅。默认由当前 agent 执行；用户明确指定或已配置委派时才使用对应工具。

1. 查对应规则条款、卡面描述及有关基础术语，确认时机、消耗、效果和来源，标明尚待裁定的部分。需要补规范描述时按[描述体系](normalized-descriptions.md)组织，不猜测或擅自扩充规则。
2. 按复杂度拆批，交代一个可交付目标、允许文件、少量核心验收、测试执行者；委派时另约定 10–15 分钟阶段预算。同类常规技能可以合批；涉及新客户端入口、公共机制或复杂濒死／用牌流程时，先交能触达主要效果的小批次。预算是阶段交回约定，不是硬超时。
3. 查锁定引擎源码和[公共实现导航](implementation/README.md)。对本批有风险的入口，先核对客户端／服务端、选择／执行、可选／必然、消耗／后续效果、当前技能／已建立持续效果这些边界，由负责人尽早审阅少量关键接口或可运行流程，再扩展实现。常规接口沿用既有机制，不要求每个技能单独审批；接口行为不能代替规则裁定。
4. 执行者打通最小正常流程，尽早触达真实选牌、选人、提示、取消和确认；由指定执行者按[测试规范](testing.md)串行验证共享运行时。优先复用公共夹具、请求辅助与套件模板，不为每批复制一套略有差异的初始化代码。玩家功能按正式扩展加载路径实现。
5. 负责人审阅阶段成果，后续只修实质缺口。再次交回时，逐项说明审阅意见为“已改且验证”“已改待验证”或“未改／原因”，附对应位置和必要证据；负责人核对状态后再给下一轮范围。失败按最短证据链定位，两次无进展即交回，不连续猜接口或重跑刷绿。
6. 每批稳定后按[分类与检索约定](implementation/README.md)更新实际受影响的技能记录，引用真实命令结果并保留边界；规则变化由负责人写回对应规范。相关实现稳定后做一次默认全量，需要发布或修改加载路径时构建并检查安装包，再更新[开发状态](status.md)。提交及 PR 按 [AGENTS.md](../../AGENTS.md) 和[项目模板](../../.github/pull_request_template.md)执行，须有用户授权。

需要委派时，交接只保留本批已确认差异、公共接口方向、文件边界及核心验收，详细依据链接到维护中的文档；不一次交付整包边界清单。不要假设接收方已读取当前聊天或自动加载项目 skill。规则类文件由负责规则判断的角色维护，委派执行者修改需按项目约定明确授权。

## 新会话入口

使用 [hanjin-content-development](../../.agents/skills/hanjin-content-development/SKILL.md) 时，通常只需给出动作和范围：

> 按照 `hanjin-content-development` 审阅蜀势力标准包。

> 根据已确认规则实装蜀势力标准包。

需要指定执行工具时：

> 根据已确认规则安排 DSH 实装蜀势力标准包。

skill 已规定上下文查找、规则核对、拆批、验证、审阅与收尾。agent 应自行核对当前分支、工作区、原文、逐将规范及状态，不要求用户重复提供仓库已有内容。整包可一次审阅，实装按复杂度分批；“实装”要求推进到范围完成，不只输出计划。未决规则不因该指令自动获批。

仅需额外提供仓库中没有的资料或裁定、特殊版本／范围限制，以及提交、推送或 PR 的授权。已有明确授权无需重复确认。新会话不能假设读过旧聊天，应以落盘记录为依据。不支持 skill 加载的 agent 可直接读取上述文件；实际自动加载能力取决于所用工具。

规则集、外部汉晋资料和用户裁定用于确定游戏语义；新月杀源码用于核对当前接口与执行流程，不能反过来替代规则。复用现有逐将规范与机制记录，不要求每次先编写整包实现说明或完整自动化测试清单。

## 维护约定

`rules/` 保留项目规范的角色及稳定引用，不能将其直接视为《汉晋规则集》。正式条文在 `rulebook/` 独立编纂，按外部基准的结构与精炼文风表达，并链接依据。编纂内容需要拆分时更新引用，旧引用确有兼容价值时保留入口，不复制两份正文。规范、API 文档和状态的变更各有依据；不要把状态过期误当规则变更。

本次整理把原规则文件的工程章节移到 `implementation/`，保留接线和验收细节，未逐一将历史卡面文本重写成规范描述。少量既有条款仍含与程序有关的解释，后续编纂时按语义核对逐步整理，不以机械删词改变已确认规则。
