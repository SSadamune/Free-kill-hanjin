## 一次内容开发

1. 查对应规则条款、卡面描述及有关基础术语，确认时机、消耗、效果和来源，标明尚待裁定的部分。需要补规范描述时按[描述体系](normalized-descriptions.md)组织，不猜测或擅自扩充规则。
2. 查锁定引擎源码和[公共实现导航](implementation/README.md)，核对客户端／服务端、事件数据类型及选择／执行职责。已有公共机制优先复用；接口属于技术实现，不是游戏语义的权威来源。
3. 打通最小正常流程，尽早验证真实选牌、选人、提示、取消和确认。面向玩家的功能默认随扩展发布，不以开发本体补丁代替。
4. 根据[测试规范](testing.md)补本轮核心回归，先定向、稳定后默认全量。需要发布或修改加载路径时构建并检查安装包；验证证据注明实际范围及未验证部分。
5. 规则歧义或实现偏差反馈到对应条款，核对来源并按必要裁定修订；更新状态表。提交及 PR 按 [AGENTS.md](../../AGENTS.md) 和[项目模板](../../.github/pull_request_template.md)执行。

跨模型交接时明确目标、允许文件、少量验收项、预算及需要读取的文档路径，不假设接收方已读取当前聊天或已自动加载项目 skill。规则类文件默认由 Codex 维护，DSH 修改需按项目约定明确授权。

## 维护约定

`rules/` 保留项目规范的角色及稳定引用，不能将其直接视为《汉晋规则集》。正式条文在 `rulebook/` 独立编纂，按外部基准的结构与精炼文风表达，并链接依据。编纂内容需要拆分时更新引用，旧引用确有兼容价值时保留入口，不复制两份正文。规范、API 文档和状态的变更各有依据；不要把状态过期误当规则变更。

本次整理把原规则文件的工程章节移到 `implementation/`，保留接线和验收细节，未逐一将历史卡面文本重写成规范描述。少量既有条款仍含与程序有关的解释，后续编纂时按语义核对逐步整理，不以机械删词改变已确认规则。
