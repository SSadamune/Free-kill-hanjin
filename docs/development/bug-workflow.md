# Bug 处理工作流

直接描述异常或提供本仓库的 Issue 编号、`#123`、Issue 链接，即可开始处理。默认先排查，在预期行为明确时继续修复和验收。用户只要求解释、审阅或汇报时，按其指定范围处理。

## 1. 接收与分诊

- 有 Issue 编号时，裸编号默认指本仓库，完整链接以其中的仓库为准。首次处理或续办均先从 GitHub 核对 Issue 正文、最新的相关评论和已关联的修复，按补充说明确认触发条件、预期行为及验收范围。若来源无法访问，先检查本地已有线索。Issue 是问题来源，提交、推送、评论、改标签、关 Issue 和开 PR 依当前授权执行。
- 用一两句话记预期、实际、触发条件及影响范围。优先级按玩家影响判断。无法开局、崩溃或导致对局状态损坏优先，其次是结算错误和关键交互受阻，再到局部显示或文案。范围广、触发频繁或难以恢复时提高优先级。
- 归因与优先级独立。可初判为规则待裁定、项目实现或资源接线、上游接口或引擎、测试或夹具、运行环境。证据不足时标为待查，可随定位修正。涉及武将技能、卡牌或规则交互时，继续使用 [汉晋内容开发 skill](../../.agents/skills/hanjin-content-development/SKILL.md)。涉及图片、音效时按[素材开发约定](assets.md)处理。

## 2. 复现与定位

- 先核对规则、实际入口及锁定的引擎接口。若涉及武将状态，记录相关的模式、主副将、明暗置、势力和触发时机。优先从玩家实际使用的入口复现，尽量固定随机状态，找出第一个偏离预期的环节。
- 优先读取现有证据。FreeKill v0.5.25 运行目录里的 `freekill.server.log` 可查扩展加载、报错和开局时间，开局这一行只记录房间号。进程重启会覆盖日志，排查时保留故障时段的片段。涉及房间设置时，有录像就先检查 `.fk.rep` 的进房数据，核对服务端下发给该客户端的禁将、禁包等设置。汉晋开局战报可另核对本局实际允许的势力。
- 当已修症状仍出现，或开发版与安装版表现不同时，先用这局的日志定位实际运行目录，再核对服务端和界面分别加载的扩展。记录工作树分支与提交、实际安装包或关键文件，以及重启后是否新开房。FreeKill 本体版本、Git 分支或推送状态各自只能证明对应一环；多个 worktree 的开发运行时需分别核对。若无法找到报错对局所用的版本，把它记作待确认，继续检查现有证据。
- 保留最短证据链。结算类问题按需核对触发、请求、回复消费、关键事件数据和最终状态。按钮检查、进入交互、选牌／选人及确认结算分别通过各自真实入口验证。引擎启动失败、断言错误及夹具污染按[失败诊断](testing.md#夹具与失败诊断)处理。
- **描述不清时**，先用已有线索缩小范围。仍无法确定异常入口时，只问能区分排查路径的问题，例如「按钮未亮，还是点开后无法选目标？」
- **正确结算不明确时**，先查卡面原文、规则集和已确认的项目裁定。几个动作之间的先后或时机关系若仍无法确定，先询问用户，再实装相应逻辑。说明已查依据、具体场景和待决定的结算，并把确认的结论写入对应规则文档。
- 区分观察结果、推测和已证实根因。间歇失败保留触发线索。未能复现时记录试过的范围、已排除的条件和剩余缺口。等待补充或裁定期间继续核对可独立验证的部分。

## 3. 确定修复范围

对每个已经确认的根本原因，全量搜索本项目中可能存在相同缺陷的实现和入口。检查共享接口的调用点，也检查独立实现中重复使用的同一逻辑、状态或假设。证据确认有同一缺陷时一并处理，修复后保留完整的横向修改清单。排查覆盖整个项目，验证可按风险选用代表性场景。

| 证据 | 处理方式 |
| --- | --- |
| 横向排查后确认缺陷仅在单个调用点 | 修正该调用点，验证正常分支和受影响路径。 |
| 多个入口的根因位于共同边界 | 优先修正公共机制，回归代表性调用者及合法例外。 |
| 职责混淆、重复实现或状态分散已导致同类缺陷反复发生，局部补丁会让调用者继续分叉 | 做范围明确的重构。说明要恢复的契约、受影响调用者和验收边界，保留现有合法行为。能单独验收的结构调整按项目约定拆分。 |

局部修复可复用已有公共接口。排查停滞时，按[测试规范的停止条件](testing.md#执行与停止条件)记录证据并调整排查路径。

## 4. 验收与结案

- 验证原失败路径及受影响的正常路径。公共修复验证代表性调用者，按[测试规范](testing.md)复用已有回归并执行相应验收。涉及界面时按[客户端验收记录](testing.md#客户端验收记录)写明覆盖范围。
- **批量修复**。同一批次包含多个问题时，每项独立修复只做定向验证，覆盖原失败路径及受影响的回归。等这一批的所有问题分别修复并通过定向验证后，再对包含全部修复的版本统一运行一次默认全量测试（`python scripts/test.py`）。
- 分别报告代码修改、已执行的验证和结果。原场景尚未验收时保留待复测项，复测通过后据此结束反馈。未证实的归因和未复现、未修正的间歇故障继续标为待查。
- 普通问题用短记录即可，必要时写入已有实现记录或开发状态。Bugfix PR 使用[项目模板](../../.github/pull_request_template.md)，在「做了什么」按 Issue 或验收批次逐项填写五列表格。

| 条目 | 根本原因 | 修改方法 | 横向排查 | 防复发策略 |
| --- | --- | --- | --- | --- |
| 原编号及玩家遇到的异常 | 写明已证实的根因，证据不足时标为待查 | 写明修复方式及行为变化，仅补回归时注明「未稳定复现，仅补验证」 | 写明按该根本原因排查的范围，完整列出实际横向修改的每个技能、效果或入口。只有原入口需要修改时，明确写明该结论 | 记录已落实的公共机制、具体回归场景或流程改进，以及待落实的措施 |

测试命令、通过数和客户端验证层级填入「如何验证」，剩余复测填入「还差什么」。

## 5. 复盘与防复发

重复发生、涉及公共机制、影响关键流程，或通过测试和审阅后仍然漏检时，按以下三项做一次简短复盘。

1. **为什么漏掉？** 找出遗漏的规则、接口假设、审阅步骤或实际验收入口。
2. **同类风险在哪？** 记录检查过的调用点和结论，特别是共享机制的其他入口及其合法例外。
3. **如何防复发？** 记录已落实的最小措施，例如真实流程回归、修正夹具、收敛接口或更新编码约定。仍待完成的措施注明状态。

有复用价值的个案归入[故障案例](lessons.md)或已有机制记录，通用做法写回测试规范或开发指南。日常处理可以写成一行摘要，依次包含现象与影响、根因与范围、修复与验证，以及必要的防复发措施。
