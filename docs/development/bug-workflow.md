# Bug 处理工作流

直接描述异常或提供本仓库的 Issue 编号、`#123`、Issue 链接，即可开始处理。默认先排查，在预期行为明确时继续修复和验收。用户只要求解释、审阅或汇报时，按其指定范围处理。

## 1. 接收与分诊

- 有 Issue 编号时，裸编号默认指本仓库，完整链接以其中的仓库为准。优先从 GitHub 读取 Issue 正文、相关评论和已关联的修复，核对用户补充及 Issue 是否仍能在当前版本复现。若来源无法访问，先检查本地已有线索。只有缺少决定排查方向的材料时，才请用户补充。Issue 是问题来源，提交、推送、评论、改标签、关 Issue 和开 PR 依当前授权执行。
- 用一两句话记预期、实际、触发条件及影响范围。优先级按玩家影响判断。无法开局、崩溃或导致对局状态损坏优先，其次是结算错误和关键交互受阻，再到局部显示或文案。范围广、触发频繁或难以恢复时提高优先级。
- 归因与优先级独立。可初判为规则待裁定、项目实现或资源接线、上游接口或引擎、测试或夹具、运行环境。证据不足时标为待查，可随定位修正。涉及武将技能、卡牌或规则交互时，继续使用 [汉晋内容开发 skill](../../.agents/skills/hanjin-content-development/SKILL.md)。涉及图片、音效时按[素材开发约定](assets.md)处理。

## 2. 复现与定位

- 先核对规则、实际入口及锁定的引擎接口。若涉及武将状态，记录相关的模式、主副将、明暗置、势力和触发时机。优先从玩家实际使用的入口复现，尽量固定随机状态，找出第一个偏离预期的环节。
- 保留最短证据链。结算类问题按需核对触发、请求、回复消费、关键事件数据和最终状态。按钮检查、进入交互、选牌／选人及确认结算分别通过各自真实入口验证。引擎启动失败、断言错误及夹具污染按[失败诊断](testing.md#夹具与失败诊断)处理。
- 区分观察结果、推测和已证实根因。间歇失败保留触发线索。找不到复现时记录试过的范围、已排除的条件和剩余缺口，继续可独立验证的部分。规则来源确有冲突或缺失时，向用户说明具体场景和分歧，取得裁定后再改对应结算。

## 3. 确定修复范围

| 证据 | 处理方式 |
| --- | --- |
| 单个调用点对一条明确规则处理错误 | 修正该调用点，检查正常分支和已知受影响路径。 |
| 多个入口共享同一接口、状态或假设，且根因位于共同边界 | 按共同调用点检查同类入口，优先修正公共机制，回归代表性调用者及合法例外。 |
| 职责混淆、重复实现或状态分散已导致同类缺陷反复发生，局部补丁会让调用者继续分叉 | 做范围明确的重构。说明要恢复的契约、受影响调用者和验收边界，保留现有合法行为。能单独验收的结构调整按项目约定拆分。 |

若证据只说明某个局部出错，仍可复用已有公共接口完成修复。同一个问题两次尝试无进展时，按[执行与停止条件](testing.md#执行与停止条件)交代证据和阻塞，避免反复重跑或扩大修改范围。

## 4. 验收与结案

- 验证原失败路径及受影响的正常路径。公共修复验证代表性调用者，复用已有回归，按风险补必要用例。玩法与接口修改先定向，稳定后按[测试规范](testing.md)执行项目要求的全量验收。涉及正式客户端接线时检查安装包，客户端实测、联网和重连分别记录。
- 报告实际修改、执行过的测试、结果和未验证项。有复现证据且修复通过时记为已修复。用户复测正常可据此结束反馈，同时保留尚未证实的根因。未复现且未修正的间歇失败继续标明待查。
- 普通问题用短记录即可，必要时写入已有实现记录或开发状态。Bug 修复的 PR 沿用[项目模板](../../.github/pull_request_template.md)，在现有小节中交代根因证据、影响范围、回归入口和未验证项。

## 5. 复盘与防复发

重复发生、涉及公共机制、影响关键流程，或通过测试和审阅后仍然漏检时，按以下三项做一次简短复盘。

1. **为什么漏掉？** 找出遗漏的规则、接口假设、审阅步骤或实际验收入口。
2. **同类风险在哪？** 记录检查过的调用点和结论，特别是共享机制的其他入口及其合法例外。
3. **如何防复发？** 记录已落实的最小措施，例如真实流程回归、修正夹具、收敛接口或更新编码约定。仍待完成的措施注明状态。

有复用价值的个案归入[故障案例](lessons.md)或已有机制记录，通用做法写回测试规范或开发指南。日常处理可以写成一行摘要，依次包含现象与影响、根因与范围、修复与验证，以及必要的防复发措施。
