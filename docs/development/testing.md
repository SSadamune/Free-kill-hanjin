# 测试分层与验收范围

本约定适用于本项目的技能、卡牌与公共规则开发。规则结算场景用于说明正确行为；**不等于每个场景都必须新增独立自动化测试**。负责人按实际风险确定少量核心验收项；委派执行者不自行将整份规范扩成逐项测试任务。单 agent 承担两种职责时同样遵循此取舍。

## 三层测试

| 层级 | 用途 | 默认处理 |
| --- | --- | --- |
| 核心行为 | 新功能的正常流程、关键分支、明确改写的规则及容易实现错误的交互 | 本轮必须验证；相关输入可合并为参数化用例，不按文字条目机械拆分 |
| 公共机制回归 | 已由引擎或项目公共套件覆盖的响应、防具、一般牌移动、阶段历史、基础国战流程等 | 复用已有覆盖；技能只补接线处的代表性集成测试，不重复验证整套公共机制 |
| 风险边界 | 特殊连锁、中途死亡、复杂替代、异常提交、少见多技能组合等 | 出现具体疑点、修复回归或改动公共入口时补测；无依据的排列组合不列为默认阻塞项 |

同一机制按改动调整层级：例如明暗置是公共机制，但技能自行预测明置后势力时，预测与真实结果一致就成为本技能的核心验收风险。不得以“公共机制”为由跳过新代码引入的风险。

## 早期接入与验证

新会话首次使用运行时，或运行环境、权限发生变化时，由唯一测试执行者先用 `python scripts/test.py --file tests/test_support.lua --timeout 180` 验证原生进程能够正常执行；同一环境已有有效结果则沿用，不为每批重复预检。原生进程无输出超时时，先区分启动／权限问题与已进入用例后的挂起，按实际权限机制处理，不直接归因于技能逻辑，也不将未执行记为测试结果。

1. 实现前用简短说明确定规则时机、消耗与效果、技能来源、目标条件，列出真正未明确的问题；核对所用回调的执行端、事件数据类型及锁定引擎中的接口。引用已有公共转换、应变和目标策略，不为每个技能重写公共流程。
2. 先打通正常流程及关键分支。复用上游技能时，获得技能或装备安装成功不能代替效果验收；至少触达一次主要效果，有特殊接口的分支需定向验证。例如方天画戟应覆盖扩目标后被闪抵消，而不只检查装备技能已附加。
3. 客户端判定尽早使用真实 `ClientPlayer` 和请求处理器验证，涵盖可用性、候选、确认及取消。提示文本须表达真实数量与限制；需要单选的界面应按单选操作验收，不能只靠确认按钮拒绝多选。涉及客户端基础设施时，增加进房、重连和普通模式隔离的针对性验收，自动化与人工结果分别记录。
4. 先定向后默认全量。涉及发布路径时，构建安装包并核对实现与注册代码已包含、开发脚本及本体补丁未混入；客户端功能应能由正式扩展加载，不能仅在已修改的开发本体中生效。需要成品运行验证时使用未应用开发适配的本体验证。

以上不是每个技能固定新增一组测试的要求；已有覆盖可复用，新入口、特殊接口或改动过的交互才补相应验证。

新增公共房间监听时，在扩展更多技能前运行 `tests/mode_rules.lua` 及与改动时机相关的已有回归（如濒死或回合末）。先核对是否仅由目标模式安装、是否会重复触发，以及纯记账是否进入玩家的触发选择；纯状态维护优先使用 refresh 通道，`global` 只用于确实需要跨模式生效的监听。相关故障与验证依据见[群包记录](implementation/generals/verification-evidence.md#qun-standard)。

## 来源与连接流程验收

公共机制首次接入正式内容时，至少用一条代表性正式武将／卡牌流程验证实际入口与主要结果，保留该内容真实的技能标签、主副将限制及所需明暗置状态。测试替身用于公共机制的其他组合覆盖；直接装上最终技能、手动补装缺失来源或仅调用最终效果，不能证明获取、升变或变更接线正确。

涉及武将牌变动时，按本批风险核对三项：旧牌来源撤回、新牌合法来源安装、其他来源保留。暗将来源相关改动须检查对应 fake／预亮状态，不能只用 `hasSkill` 代替来源断言；同名技能仍由另一张牌或角色独立效果提供时，也不能要求它整体消失。真实结果可合并在同一个用例中，已覆盖的公共机制直接复用，不要求每名武将或每种操作穷举全部来源组合。

例如张角普通升变应走真实升变入口，观察旧雷击／鬼道预亮来源是否撤销、弘法是否获得并实际建立旗来源，以及暗副将与独立同名来源是否保留。不能用“测试君主升级成功”和“直接获得弘法后授旗成功”两项局部结果替代。阶段记录说明实际入口、关键观察结果及未验证部分即可，不另建全面映射表或以测试数量作为交付门槛。

## 共享运行时调度

- 每批交接明确谁负责运行测试；并行实现者可以编辑各自文件、做静态检查，只有指定执行者同步和运行共享 `.dev/runtime`。交接测试槽时须确认前次测试已退出，并使用当前稳定的工作区内容。
- 测试通过 `python scripts/test.py` 执行。入口在依赖核对、同步、游戏进程运行期间持有同一运行时的进程间锁；占用时快速失败，不等待无限，也不关闭别人的游戏。异常退出释放锁，不靠删除残留锁文件解锁。
- 直接执行 `scripts/dev.ps1` 的同步／启动不受测试入口锁保护，仍须遵守上述调度；不要绕开占用提示改用备用运行时继续宣称验收。需要独立环境时，先确认引擎、依赖、适配与同步内容等价，并单独说明验证环境。

## 公共辅助与套件模板

- 新套件从 [skill_suite.lua](../../tests/templates/skill_suite.lua) 复制到 `tests/`，一并重命名 `Testqiao_skill_template` 测试类与返回描述符的 `qiao_skill_template`，填写真实主流程用例，再将文件名加入 `tests/all.lua`。模板本身不纳入默认套件；未填测试的空模板不能当作验证通过。
- 使用[国战房间辅助](../../tests/support/hegemony.lua)的 `initQiaoRoom()` 建房；在 `FkTest.runInRoom` 内调用[技能测试辅助](../../tests/support/skill_test.lua)的 `installBlankGenerals(room, kingdoms)` 安装已知白板，或用 `installDualGenerals(room, player, { main, deputy, kingdom, hp? })` 安装已知组合。辅助通过正式明置／换将清旧来源，更新 `__heg_*` 后重算体力；仍须由用例建立本技能需要的牌、阶段和历史。
- 优先使用官方 `FkTest.setNextReplies` 队列控制真实请求。确需覆盖请求方法时，用 `withSkillRequests(room, skillName, overrides, fn)` 限定所属技能，非目标请求委托原方法；退出或异常后恢复原方法。处理器参数为 `(self, player, params, original, ...)`，可在其中继续调用原请求。辅助负责恢复与重抛错误，不代替真实效果断言。
- 公共辅助的回归见 [test_support.lua](../../tests/test_support.lua)，吴包辅助套件已示范复用。后续仅按明确的重复需求扩充，不一次迁移所有旧套件，也不为每个技能新增一套公共回归。
- 修改运行时锁或 Python 入口时，运行 `python -m unittest discover -s tests/python -p "test_*.py" -v`；修改 Lua 辅助时先运行 `python scripts/test.py --file tests/test_support.lua --timeout 180` 及实际受影响套件，稳定后再做默认全量。

## 夹具与失败诊断

- 客户端用例同时建立真实 `ClientPlayer` 与对应客户端房间，确认 `player.room == nil`、`Fk:currentRoom().players` 为客户端角色；不能让公开房间查询暗中返回服务端对象。可参考 `tests/qun_basic.lua` 的 `withClientRoom`，独立复制本例会修改的牌区与历史，异常后恢复上下文。通过真实请求处理器验证合法场景可用及一个无合法候选的禁用场景；只断言不抛异常不足以证明正确。
- 夹具应明确建立本例所需状态，并检查关键前置条件。更换国战双将时，处理原暗将技能、预亮状态、技能来源、势力与相关标记；不能只修改将面和当前势力。使用引擎或项目已有流程清理来源，重复准备操作适合在确认共性后提取为少量公共辅助函数。
- 性别、势力等资料影响目标条件时，使用真实正式武将验证一次允许与拒绝的目标，不只断言注册表与数据表一致。同类真实请求先跑通一个用例，再复用其回复与探针；观察探针须必然执行且对同一事件只记录一次，不能让默认取消掩盖重复询问。
- 普通功能测试建立明确场景；随机初始化可作补充稳定性验证。随机失败时记录可复现输入或初始双将、关键标记、技能状态和请求／回复消费，再把已确认原因缩成确定性回归。固定种子可用于复现，不能用特定种子掩盖失败。
- 首次出现间歇失败即保留为未解决问题，不能凭随后一次通过认定已排除，也不能无证据归因为“时序抖动”或“既有问题”。区分断言失败、夹具污染、进程启动失败和测试未执行；模型自述不代替命令输出。稳定性重复运行只用于验证具体修复，不用于刷出全绿。
- 用实际触发、回复、牌移动、使用次数和伤害等可观察结果验收；避免只调用效果函数而绕开本次需要验证的发动和客户端流程。
- 失败交回提供最短证据链：关键前置状态、触发条件是否成立、请求名与所属技能、回复消费、主要事件数据及最后失败断言；区分“没有触发”“输入错位”“接口执行错误”和“断言自身挂起”。不能在尚未检查这些步骤时，把推测写成根因。

## 故障记录的保留范围

有明确复用价值的故障保留简短的“现象／触发条件、根因、修复方式、回归入口”，放在所属武将或公共机制的现有规范中。通用约定集中写入本文或项目约定，由案例引用，不重复另定规则。记录应能帮助后来者识别同类问题，不累积完整聊天、逐轮尝试、催办过程或重复的历史测试数量。

案例修复后标明已修复；未确定的根因标明仍在调查，不写成既定结论。临时诊断文件在交付前决定移除或整理为正式工具，不能仅以临时文件名长期混入默认开发入口。

## 执行与停止条件

1. 首轮优先交最小可运行实现和核心测试；审阅后只补明确缺口。默认不要求完整场景映射表、固定测试数量或每轮独立子代理审阅。
2. 开发中先运行相关定向套件。相关改动稳定后运行一次 `python scripts/test.py`，保留默认国战套件作为最终验收入口；不以精简为由跳过项目必需检查。
3. 已通过检查只有在新增相关修改、出现失败或仍有明确疑点时才重跑。相同问题两次尝试未解决时交回证据与阻塞，不无限扩测试夹具或连续重跑全量套件。
4. 委派协作中，同一轮以约 10–15 分钟为交付预算，约每 5 分钟简报；到预算或里程碑即交回阶段成果。阶段成果可未完成，但须说明尚未验证的风险，不能写成已验收。
5. 交付仅需改动文件、完成能力、真实执行命令／结果与未完成项。可用合并场景说明覆盖，不要求一条规则对应一个测试函数。

## 保留与精简

- 优先合并同一逻辑分支的重复准备与断言，避免用例间状态泄漏；测试应验证可观察结果或实际事件，避免只模拟并重复实现内部算法。
- 不为减少数字而删除已有有效回归。删除或合并必须确认覆盖没有丢失；测试代码减量可单独安排，不阻塞与其无关的技能交付。
- 公共套件的失败应区分本次回归与已有问题，不屏蔽失败、不通过修改预期凑通过。
- 汉晋技能 `addTest` 仅在汉晋测试房间运行；新技能测试纳入默认国战套件。`--skills` 使用官方默认房间，仅作工具或上游测试验证，不代替汉晋行为验收。
- `docs/rules/` 的记录由负责规则判断的角色依据可核验交付更新。委派执行者默认只读；计划、模型自报及未执行用例不能写成验证通过。
